# Testing Vocabulary

The terms test engineers use to judge a test suite or a test plan, so a review
names the gap the way the field does and points at something a reader can see
in the tests, the CI run, or a coverage or mutation report. Authors and check
scripts use it; reviews do not load it by default. A term is admitted only with
a registered source and an observable marker; evidence and access dates are in
`sources.json`. Check: `exact` (a pattern in the tests or a report a script can
match; none ships here yet, so no rule ids), `jev` (a typed question), `judge`
(a person or model decides).

| Term | Definition | Source | Marker | Check |
|---|---|---|---|---|
| Test pyramid | Many small fast tests, fewer coarse ones, very few end-to-end, chosen by granularity. | [SRC-TEST-001] | Logic a unit test could pin down covered only by an end-to-end test. | judge |
| Testing trophy | Static checks at the base, then unit, a wide integration layer, and few end-to-end tests, weighed by return on confidence. | [SRC-TEST-002] | A suite whose units mock every collaborator while no test runs two real parts together. | judge |
| Static checks | Type checking and linting that catch a class of defects before any test runs. | [SRC-TEST-002] | A CI pipeline with no typecheck or lint step ahead of the tests. | exact |
| Test size | Small, medium, or large by the resources a test may use (network, database, files, threads, sleeps) and its time limit. | [SRC-TEST-003] | A test filed as unit that opens a socket, a database, or the file system, or sleeps. | exact |
| Ice-cream cone | A suite inverted toward end-to-end and manual tests. | [SRC-TEST-001] [SRC-TEST-009] | More end-to-end than unit tests by count; most regressions first caught by end-to-end runs. | exact |
| Hourglass | Many unit and end-to-end tests, few integration tests, usually because parts cannot be built in isolation. | [SRC-TEST-009] | No test exercises two components together; failures between tiers surface only end to end. | judge |
| Consumer-driven contract | A contract generated by the consumer's tests and verified in the provider's build. | [SRC-TEST-004] | Two separately deployed services that only mock each other, with no contract verified by the provider. | judge |
| Contract by example | A contract made of concrete request and response pairs rather than a static schema. | [SRC-TEST-004] | An API change checked only against an OpenAPI schema while consumers depend on specific values. | judge |
| Surviving mutant | A small deliberate code change that no test detects. | [SRC-TEST-005] | Survived mutants on changed lines in a mutation report. | exact |
| Code coverage | Which lines or branches the tests execute; a finder of untested code, not a grade. | [SRC-TEST-008] [SRC-TEST-009] | Changed lines with zero coverage in the diff report. | exact |
| Behavioral test | A test whose result changes when the behavior changes. | [SRC-CODE-002] [SRC-TEST-005] | A behavior break, by hand or as a mutant, that every test still passes. | judge |
| Structure-insensitive test | A test whose result does not change when only the structure changes. | [SRC-CODE-002] [SRC-TEST-007] | A pure refactoring that forces test edits. | judge |
| Implementation detail | Something a user or caller cannot observe: private state, internal method names, component internals. | [SRC-TEST-007] | A test that reads private fields, spies on internal methods, or asserts component instance state. | judge |
| Specific test | A failing test whose cause is obvious from its name and message. | [SRC-CODE-002] | A failure message such as `expected true, got false` with a name that names no behavior. | judge |
| Deterministic test | A test whose result does not change while nothing changes. | [SRC-CODE-002] [SRC-TEST-006] | The same commit passing and failing across reruns. | exact |
| Quarantine | A separate suite for non-deterministic tests, bounded by count or time, so the healthy suite keeps its signal. | [SRC-TEST-006] | A flaky test skipped or retried with no owner, no limit, and no fix date. | judge |
| Bare sleep | A fixed wait for asynchronous work instead of a callback, poll, or completion signal. | [SRC-TEST-006] | `sleep`, `setTimeout`, or `waitForTimeout` before an assertion in a test. | exact |
| Hermetic test | A test whose dependencies are all under its control. | [SRC-TEST-010] [SRC-TEST-003] | A test that calls a real external service or reads the wall clock. | exact |
| Test double | A stand-in for a production collaborator: dummy, fake, stub, spy, or mock. | [SRC-CODE-013] [SRC-TEST-010] | A double for something the test could run for real fast and deterministically. | judge |
| Realism over isolation | Use the real implementation when it is fast and deterministic, a fake next, a stub or mock last. | [SRC-TEST-010] | A mock where a real object or an in-memory fake exists. | judge |
| State testing | Asserting the result or resulting state, not the calls made on the way. | [SRC-TEST-010] [SRC-CODE-014] | A test whose only assertions verify calls on mocks while the outcome is observable. | judge |
| Given When Then | A behavior stated as preconditions, one stimulus, and an observable outcome. | [SRC-CODE-015] | A test with several stimuli, or a Then that asserts internal state rather than an outcome. | judge |
| Regression test | A test added with a fix that fails without it. | [SRC-TEST-009] [SRC-CODE-001] | A bug fix PR with no test, or a test never seen failing before the fix. | judge |
| Failure-path test | A test that injects the error, timeout, or unavailable dependency and asserts the handling. | [SRC-TEST-009] | Error, retry, and timeout branches with no test that drives them. | judge |

## Not admitted

- "100 percent coverage", or any fixed coverage number, as a goal: a target
  turns into a ceiling and invites assertion-free tests [SRC-TEST-008]
  [SRC-TEST-009]; use coverage to find untested changed lines.
- A test shape as policy: the pyramid, the trophy, or a fixed ratio such as
  70/20/10, and the ice-cream-cone warning turned into a quota; the mix follows
  the architecture and the risk [SRC-TEST-009] [SRC-TEST-001].
- "Never mock": doubles are right for slow, nondeterministic, or external
  dependencies [SRC-TEST-010]; the defect is a double where the real thing
  would do.
- "Mock everything for a pure unit test": prefer realism over isolation
  [SRC-TEST-010].
- "It is just flaky, rerun it": non-determinism is a defect to quarantine and
  fix [SRC-TEST-006].
- Debating whether a test is "unit" or "integration": name its size by the
  resources it uses [SRC-TEST-003].
